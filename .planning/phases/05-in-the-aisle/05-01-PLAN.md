## Phase Goal

**As a** patient talking to the dietitian in a store, **I want to** always get a spoken answer when I ask a question, **so that** I can decide what to buy without repeating myself or hanging up.

<objective>
Make sure a spoken question always gets an answer. Gemini stops treating caller noise as barge-in (D-16), and a reply watchdog nudges the model once when a caller turn ends with no reply and no tool run (D-17). Six simulated calls prove it (D-18). This protects everything already built and has to land before the in-aisle features in 05-02 and 05-03.

Purpose: about one simulated call in four dropped the reply (D-15). In a store that would sound like the agent ignoring the patient.
Output: agent/turns.mjs and its tests, a tool-activity hook in agent/tools.mjs, wiring in agent/agent.mjs, replyNudge in agent/prompt.mjs, AGENT_ALLOW_BARGE_IN in .env.example, and the D-18 proof in the SUMMARY.

Read at commit 72d84d3 (branch agent, HEAD "docs(04): add code review report"). Here is what the installed packages do, which the executor relies on:

- `@google/genai` 3.3.0 (a root dependency) exports `enum ActivityHandling { ACTIVITY_HANDLING_UNSPECIFIED, START_OF_ACTIVITY_INTERRUPTS, NO_INTERRUPTION = "NO_INTERRUPTION" }` and `interface RealtimeInputConfig { automaticActivityDetection?, activityHandling?, turnCoverage?, ... }`. The plugin carries its own nested @google/genai 2.32.0 with the same string value. `node -e "import('@google/genai').then(m=>console.log(m.ActivityHandling.NO_INTERRUPTION))"` prints NO_INTERRUPTION.
- `@livekit/agents-plugin-google` 1.8.0 `RealtimeModel` constructor options include `realtimeInputConfig?: RealtimeInputConfig` (dist/realtime/realtime_api.d.ts line 161). The constructor copies it into the Live session config (realtime_api.js line 1035-1036). Server-side turn detection stays on unless `automaticActivityDetection.disabled` is set, so leave that field out. The plugin's own `interrupt()` returns early when `activityHandling === ActivityHandling.NO_INTERRUPTION` (line 550).
- Caveat that matters for D-15 and D-16: the plugin emits `input_speech_started` (a) on a server `interrupted` flag (lines 831-833, 1169-1170) and (b) whenever a new server-started generation is created (line 1091). `AgentActivity.onInputSpeechStarted` in `@livekit/agents` 1.8.0 (dist/voice/agent_activity.js line 1169) then sets user state 'speaking' and calls the framework's own `interrupt()`, which cancels the current SpeechHandle, including a tool that is running. The D-15 debug log shows exactly this. The question's generation issued a `check_food` tool call. A new server generation started 3 ms later ("onInputSpeechStarted", "Creating speech handle"). Then came "Aborting all realtime generation tasks due to interruption", the tool never finished (no "tools execution completed", no `[agent] tool check_food` line), and nothing followed. NO_INTERRUPTION stops server-side barge-in, but it cannot stop this framework-level cancel. The D-17 watchdog is what guarantees an answer. Record this in the SUMMARY.
- `@livekit/agents` 1.8.0 `voice.AgentSessionEventTypes`: `UserStateChanged = "user_state_changed"`, `AgentStateChanged = "agent_state_changed"`, `FunctionToolsExecuted = "function_tools_executed"` (dist/voice/events.d.ts lines 13-30). `UserState = 'speaking' | 'listening' | 'away'`, `AgentState = 'initializing' | 'idle' | 'listening' | 'thinking' | 'speaking'`. Events carry `{ oldState, newState, createdAt }`. With this realtime model and no VAD passed, user state comes only from the plugin. It becomes 'speaking' when a server generation starts and 'listening' when that generation is marked done (agent_activity.js lines 1169-1196, realtime_api.js line 942). So "caller turn ended" really means "the model's turn for that speech ended". The watchdog therefore counts the agent as having answered if it spoke at any time after the turn started, not only after it ended. `_updateUserState` emits only on a change.
- `session.generateReply({ instructions })` returns a thenable SpeechHandle (awaiting it waits for playout). It throws synchronously if the session is not running. The plugin sends the instructions as a model turn plus a "." user turn, and rejects after 5 s if no generation starts. If a server generation is already running, the new speech is queued behind it. It is safe to call while nothing is being generated, which is how the greeting already works.
- The framework warns (does not throw) that `allowInterruptions` cannot be false with server-side turn detection (agent_activity.js lines 292-295). Do not set session or agent `turnHandling.interruption`.
</code_reading>
